# RemoteConfigSchema library

One `RemoteConfigSchema` manifest per OpenTelemetry Collector release and
distribution. Each lists the components that release ships — the signals they
handle, their per-signal stability, their Go module, and the settings they accept —
so a remote config can be validated against the collector build it will actually run
on rather than against every component that exists upstream.

Files are named `<binary>-<version>.yaml`; the binary is the one the upstream
releases publish (`otelcol`, `otelcol-contrib`, `otelcol-k8s`, `otelcol-otlp`).

The apiserver seeds these on startup according to `bootstrap.remoteConfigSchemaLoad`
(`latest` by default, which seeds the newest version of each distribution).

## Where they come from

These are rendered from the
[otelcol-config-schemas](https://github.com/minuk-dev/otelcol-config-schemas)
registry, whose files are generated by `tools/schemagen` in
[otelcol-config-lint](https://github.com/minuk-dev/otelcol-config-lint) from each
release's upstream `metadata.yaml`, its components' `Config` structs, and the
`config.schema.yaml` the collector publishes from v0.150.0 on. The linter reads that
same registry, so a config checked locally with `otelcol-config-lint` is checked
against the same catalog this server holds.

Field documentation is dropped on the way in: it is most of the bytes and none of
the checks.

**Do not edit these by hand.** Regenerate them with:

```sh
make gen-remoteconfigschema                        # every release the registry has
DISTS=contrib VERSIONS=v0.157.0 hack/gen-remoteconfigschema.sh
SCHEMA_LOCATION=../otelcol-config-schemas hack/gen-remoteconfigschema.sh
```

A release the registry does not cover — a custom distribution, or one built
in-house — does not belong here. Generate it from the binary itself, which reports
the components it has but not their settings:

```sh
opampctl generate remoteconfigschema --binary-path ./otelcol-custom | opampctl create -f -
```
